🔍 OOP Relationships — Where & Why

GENERALIZATION (Inheritance — Solid line, open triangle)

  • ScoredSegment extends StreetSegment — A scored segment is-a street segment enriched with computed model metrics (risk, band, exposure, confidence). The parent interface models raw OSM geospatial and physical road data; the derived interface attaches model outputs while guaranteeing complete backward compatibility. Any consumer expecting a StreetSegment (such as hospital distance computation or geometry rendering) can transparently accept a ScoredSegment (Liskov Substitution Principle).
  • HospitalRisk extends Hospital — A hospital-with-risk is-a hospital enriched with dynamic approach accessibility metrics (accessRisk, approachRoads, worstRoad, status). The base interface represents static health infrastructure from OSM; the specialized interface joins dynamic street flood risks to medical facilities.

COMPOSITION (◆ Filled Diamond — Strong ownership / "Parts die with the whole")

  • WardData owns StreetSegment[], Depot[], RainPoint[] — When a ward snapshot is discarded or refreshed, all constituent segments, depots, and precipitation data points are discarded with it. They possess no independent lifecycle outside of their parent ward context.
  • AllocationResult owns Assignment[] — Dispatched truck assignments exist solely as the solution set of a specific VRP optimization run. When re-allocation is computed for a new scenario, previous assignments are destroyed alongside the previous result object.
  • Config owns WardConfig, FleetConfig, Paths — The Python backend constructs a unified immutable configuration hierarchy from ward_config.yaml. The sub-configurations exist exclusively as fields of the root configuration.
  • FleetConfig owns Depot (Python)[] — Municipal depots are defined and parsed directly inside the fleet configuration block and validated together in __post_init__.

AGGREGATION (◇ Open Diamond — Shared reference / "Part can exist independently")

  • Truck references Depot — A dewatering truck is assigned a home base depot from which it departs and to which it returns. The physical depot infrastructure has an independent existence: it outlives any individual truck, route shift, or operational plan, and is shared across multiple trucks.

ASSOCIATION (→ Solid Arrow — Structural relationship / Reference)

  • Assignment → ScoredSegment — Each scheduled truck task references the specific target street segment requiring dewatering. The segment is not owned by the assignment; it remains in the ward-wide segment repository.
  • Assignment → Depot — The assignment records the departure depot origin of the dispatch leg.
  • HospitalRisk → AccessStatus — Each hospital's calculated accessibility is classified using the five-state AccessStatus enumeration (cut-off, at-risk, watch, clear, unknown).

DEPENDENCY (- - ▷ Dashed Arrow — Usage / "Uses" / Parameter)

  • ScoredSegment → RiskBand — The scored segment categorizes computed flood probability into the RiskBand enum (critical, high, moderate, low).
  • ScenarioOverrides → ScoredSegment — The scoring engine function scoreSegments(ward, overrides) consumes scenario parameters (rainfall rate, pump status, drain clearances) to dynamically compute risk.
  • DataPipeline → WardData — The server data pipeline orchestrates OSM, SRTM elevation, OSRM distance matrices, and Open-Meteo forecasts to construct and return a unified WardData instance.
  • DataPipeline → RainNow & GeoUtils — Pipeline delegates geodesy calculations (Haversine distances, path midpoints) to GeoUtils and yields real-time rainfall status via RainNow.
  • JalNitiService → DataPipeline & model — Server actions delegate external fetching to DataPipeline and algorithmic calculations (VRP orienteering optimization, hospital risk joins) to the model layer.
  • DashboardUI → JalNitiService — The React UI invokes server endpoints via TanStack Query for reactive, real-time dashboard updates.
  • DataSources (Python) → DiskCache & Config — Offline pipeline scripts query satellite and meteorological APIs according to Config parameters, routing all raw responses through deterministic disk caching.

📋 Summary for Presentation

This diagram covers the four core modules of JalNiti:

  • Module 0 (Domain Data & Types) — 8 interfaces & enums defining the system's foundational entities: ward boundary geometry, street segments, municipal depots, precipitation time series, and hospital infrastructure.
  • Module 1 (Risk Scoring) — Multi-criteria geospatial risk modeling incorporating elevation, slope, water body proximity, and road network density, dynamically tuned via ScenarioOverrides.
  • Module 2 (Resource Allocation - VRP) — Solves a Team Orienteering Vehicle Routing Problem (TOP-VRP) using value-density greedy construction and 2-opt/relocate local search heuristics to generate operational Assignments.
  • Modules 3 & 4 (Pipeline, Service & UI) — Dual TypeScript/Python ingestion layers fetching from Overpass, OpenTopoData, Open-Meteo, OSRM, and IMD; coupled to a Next.js/React dashboard via clean server action interfaces.
